# 汇报与回复回源

## 唯一汇报入口

向用户提问、答复或汇报，读取 `botmux skill show botmux-report` 并按技能调用。该内置技能包装现有 `botmux human-session --input <JSON文件|->`，不新增第二套汇报实现。原群、原会话和来源 bot 由实际运行上下文提供；现有能力负责建汇报群、登记来源、展示正文和回复回源。

启用汇报能力的会话在既有每轮提示里看到三条分流说明：面向用户走 `botmux-report`，每次独立汇报、回复回原群、继续答复再用一次；用户明确要求本群回复或 bot 间沟通走 `botmux send`；`create-group` 只用于工作子群。初始共享说明、send 技能描述和底层命令帮助同步使用这一区分。未启用的会话保持原提示；安装配置里的旧 `skillEntry` 名称不变，不借此扩大启用范围。

按 bot 启用时，提示生成使用会话传入的真实 `larkAppId`：daemon 的新消息/续轮来自 `ds.larkAppId`，CLI 初始 system prompt 来自 worker 的 `cfg.larkAppId`。daemon 启动本来就会清除继承的会话环境变量，不能依赖其中的 `BOTMUX_LARK_APP_ID` 判断提示是否启用；不修改这项清理或配置开关。

本次不拦截或修改 `create-group`，不根据群名猜测用途，不自动接管已有普通群。过去经普通建群、普通发送形成的未登记汇报，不会因安装技能而获得回源关联；其原群、原卡片、原消息均保留，旧回复不会自动补发。新的汇报应从上述唯一入口发起。

## 独立汇报：不等待业务结束

每次技能只调用一次 `operation=report`，提交 `requestId`、`direction=assistant_answer`、`title` 和 `body`。提问、答复和进展都用这一种形式；每次新汇报创建新群。无需读取/确认细则、冻结事实、模型检查或领取/消费回复。正文仍需写清必要背景、事实与未知，由调用者对内容负责。

调用完成只表示这条汇报正文及原群链接已送达，不表示用户已回复或业务完成。后续汇报不占用旧请求的排队槽位，不等待旧回复被消费，也不取得回答输出锁。旧群的新回复仍带着对应汇报正文回到原群，作为普通消息唤醒原 bot；需要继续答复就再次调用技能。

这是业务层无会话状态，不是删除投递记录：仍保存来源关联、发送意图、消息 ID 和去重记录，防止断线后重复建群或重复回源。同编号且正文相同的调用核对原投递，不创建第二个群；结果未知时不换编号盲重发。旧账本和旧请求保留，不伪造业务消费或自动迁移。

技术调用链：本地 CLI 复用现有 `fetchDaemonIpc` 的 host HMAC → daemon 验证请求 → source runtime 从真实活动会话及已配置来源派生 frame → 既有 executor/ledger/Lark transport。独立 report 不依赖易随 worker 回合结束而撤销的 originCapability；旧 human-session 操作仍使用原来的回合凭据，不修改 worker 的终止判断、身份方向规则或其它 IPC 路由。适用范围仍为已启用回复回源的本地非隔离 pty/tmux 会话，未扩大到 sandbox、远程或 adopted 会话。

自测直接读取技能 JSON 示例，覆盖真实 CLI/HTTP 鉴权、连续独立汇报、原回合结束后的新汇报、用户原文回源、真实 mention 的传输格式、重复来信和重载后按需接线。测试中的 Lark 为隔离夹具，不等同于真人线上测试；原质量检查与事件消费协议另做兼容回归。

### 用户测试与副作用

在原工作群让 bot 汇报一件事，在生成的汇报群回复；应看到原群中自己的原话、对应汇报背景和对原 bot 的真实 mention。连续问答会产生多个汇报群，这是本次选择；无需在旧群“标记结束”。新入口不再有独立模型的正文审核，减少等待和误拒，但也不承诺自动发现内容遗漏。重发同一条消息不会重复回源，两条不同消息则分别转发。

已存在的旧多阶段请求继续保留旧语义；本次不替它消费历史事件。停机窗口的自动补消息限制不变，详见下文。其它 CLI 的终止信号、工作子群、普通发送、身份回退和未启用会话不作行为变更。

## 回复回源实现

用户在汇报群回复后，原问题、对应汇报消息、回复消息和逐字原话一起回到来源会话，并真正 mention 来源 bot。

现有 `receive → relay → send intent → Lark transport → readback` 链保持不变；独立汇报到此完成回源，不再建立业务 claim/consume 收件箱。配置了 `replyForward` 的安装使用 `lark-cli --as user` 发送；只有用户身份明确被拒绝时使用配置中唯一的回退 bot。网络超时、限流和未知发送结果不切换身份。展示汇报与发送群链接仍使用来源 bot。

安装文件增加 `replyForward: { userProfile, fallbackProfile, fallbackAppId }`，值来自部署环境中已核实的用户 profile 及指定回退 bot。历史安装文件与已经保存的发送回执继续可读。实际部署只指定一个回退 bot，不自动挑选其它身份。

目标 bot 来自该次请求的来源 app；通过现有成员映射按发送 app 解析 mention。群级会话发回原群；话题级会话回复原话题。新的消息通过正常 IM mention 接收路径继续原会话，不再重复调用内部 trigger。旧请求收件箱的领取与消费回执继续保留，新 report 不生成这些业务状态。

发送回执保存实际发送身份，回读核对消息、正文和 mention。真人原始正文始终独立保存，只有发送回读可以去掉传输添加的 mention 前缀。

非 IPC 的回复子 CLI 不继承 daemon 的 IPC 通信环境变量；处理范围包括该链的成员查询、用户发送和唯一回退发送，不改 worker 的 fork 环境。成员查询失败明确记为 `NOT_SENT`，原发送意图允许显式同内容重试；发送调用开始但回执不确定仍记为 `UNCERTAIN`，不得盲重发。

daemon 没有单一聊天上下文。实际发送时使用已核实的 `frame.source.appId/sessionId/chatId`，沿 runtime → Lark transport → 子 CLI 传入 `BOTMUX_LARK_APP_ID/BOTMUX_SESSION_ID/BOTMUX_CHAT_ID`；不从父进程偶然残留的群号推断，不改变本地身份方向检查。

启动不主动重绑汇报群监听。启用回复回源配置后，由下一条真实来信触发已有 `connectRoom`，按需重绑原来源接收回调；不新增队列、不恢复关闭的业务会话，也不改原有回答输出约束。

本版本明确不自动扫描或排空已落盘的 `delivered:false` 历史事件。停机窗口内到达而未交付的来信不会由本功能自动捞回，需要用户重新发送一次。这是本次选择：避免旧语境中的回复被自动再次推送；代价是用户必须重新发一次，系统不会自行补齐。自动启动排空仅保留为非阻塞待办，未来若实施也只能处理真实落盘记录，不能据此保证找回未进入本地的离线消息。

本次联调的历史失败回放保留原消息、审计标识、原始发送意图与失败文件；当前版本不会自动补发，也不会把失败记录覆盖为成功。逐笔审计确认本次已进入本地发送命令的失败由缺失来源聊天上下文而被身份方向检查拒绝；IPC 环境清理按自身用途保留，不作为这些失败的根因。

影响范围限于启用该配置的人类会话回传；不更改其它 CLI、后端或普通发送流程。验证覆盖用户身份成功、明确拒绝后的唯一回退、未知发送结果、身份回读、重复事件、旧回执和原会话收件箱消费。

## 来源工作群正常发言

来源工作群不再因为历史回答的 `outputFence` 记录而整群禁止发送。传输层只按目标群工作，不能把某一轮的回答状态当成整个工作群的长期禁言开关。进展、后续答复和本群闭环可以正常发送，无需等待历史回复全部补齐。

本次只移除来源工作群的整群拦截，不删除保护记录或失败事件；专用汇报群隔离、回源事件去重和身份检查不变。自动最终答复仍由既有 turn-scoped（仅对应回合）抑制处理；主动发送的普通群消息不再用整群禁言防重复。私聊检查不在本次改动范围。
