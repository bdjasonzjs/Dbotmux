# 汇报规范

目标：让完全不知道前情的人，只看这一条汇报，就明白在说什么、现在怎样、是否需要自己做什么。

每次准备汇报前，完整阅读本规范，再组织正文。规范是写作要求，不新增阅读回执、审核模型或业务状态。

## 六条要求

1. **一次只说一件事。** 能分别答复、分别决定的事项，要拆成多次汇报，不能打包“顺便说一下”。同一件事的背景、结果、依据和风险可以放在一起，不必拆散。
2. **不使用开发过程中的代号。** 标题和正文用实际产品、功能或问题的名称，不写“S1/S2”“切片三”“某某 v5 已绿”等内部简称。必要技术术语第一次出现时说明含义。排查编号、提交号和日志放核查材料，不让读者靠这些猜事情。
3. **把读者当作没有任何前置信息。** 写清具体对象、要解决的问题，以及为什么现在汇报。不能用“这个”“那条链路”“按刚才的方案”代替说明，也不能假设读者记得自己问过什么。
4. **直接回答，简洁但不省略关键事实。** 先给容易理解的结论，再补必要背景和依据。说明哪些已完成、哪些尚未做、对用户有什么影响；事实、推测、建议分开。只做了本地测试，就不能说线上已验证；发送成功也不代表事情办完。重要限制、代价和未知不能为了简短而删掉。
5. **说清是否需要用户行动。** 需要决定时，解释具体选择、差别与后果，有真实截止时间再写；建议标明是建议，不替用户决定。不需要决定时直接讲结果，不硬凑选择题、不要求回复“收到”，不把沉默当同意。
6. **正文能独立读懂。** 链接、附件和消息编号只用于核查，不能代替背景、结论或待决定事项。删掉无关进度、重复确认、流水账和仪式化套话；不要把多个事项藏进附件后仍当成一次汇报。

## 写法参考

不是固定表单，按这一件事实际需要组织几句话即可：

- 结果或进展：具体事情与结论 → 必要背景和依据 → 对用户的影响、尚未验证的部分。
- 需要决定：现在要解决的问题 → 具体选择及各自代价 → 只请用户决定这一件事。

不要写：“导出 S3 已绿，等线上验收；顺便汇报登录优化。”

可以写：“网页导出为 PDF 的功能已完成开发，本地测试能保存文字和图片，但还没有部署。上线后的下载效果尚未验证，现在不能用于正式交付。”

登录优化是另一件事，另发一条汇报。

## 发送前自查

不看聊天历史，只读标题和正文：能否知道具体在说什么？是不是只有一件事？有没有内部代号或缺失背景？结论、依据、限制和需要用户做的事是否清楚？有缺项就先改正文，不把理解成本留给用户。

用户回复后，由原业务继续处理；要进一步答复，就再次使用汇报能力。不要在旧汇报群追加新的汇报，也不要求用户或 bot 领取、消费、标记结束。
